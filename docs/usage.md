# 使用指南

## 选择仓库与基点

打开受信任且至少有一个提交的 Git 项目后，从活动栏进入“ReviewSlate”。多仓库工作区可在“变更文件”的更多菜单中选择仓库，每个仓库分别保存记录。

点击“选择基点”时有两种语义：

| 选择 | 本轮基点 |
| --- | --- |
| 本地或远端分支 | 该分支与当前 `HEAD` 的共同祖先 |
| 指定提交 | 选中的提交本身 |

选好后固定为 SHA，右侧始终是当前仓库磁盘上已保存的工作区。它包括相对基点的分支提交、暂存和未暂存改动的最终结果，以及未被 Git 忽略的未跟踪文件；暂存区不是独立的一侧。只在暂存区存在、但已在工作区撤回的改动不会单独显示。

“对比起点”显示来源、提交说明和短 SHA，可用旁边的复制按钮取得完整 SHA。扩展不会自动 fetch；选择前需要的远端更新由你自行完成。

在更多菜单中设置“本仓库默认基点”，可以让任意本地分支、远端分支或固定提交置顶。此设置只影响之后的选择，不改变当前 CR。未设置时优先使用 `upstream/HEAD`、`origin/HEAD`，再查找远端 `main` / `master` / `trunk`，最后回退本地主分支。

部分宿主的 Git 图形提交菜单提供“以此提交为基点创建 CR”。它使用该节点所属仓库与提交，对比当前检出分支的工作区，不切换分支。该入口依赖宿主对 `scm/historyItem/context` 的支持；菜单不可见时，使用通用的“选择基点”入口。汇总节点不代表可选择的提交。

## 看 Diff 与记录进度

点击文件打开完整 Diff，左侧是固定基点，右侧是工作区文件。普通 UTF-8 文本可在右侧直接编辑、保存；编辑器会显示尚未保存的输入，但审阅状态以磁盘上已保存的内容计算。左侧快照、上次审阅后的增量视图、删除文件、符号链接、二进制和纯类型或权限摘要只读。

同一 CR 的同一文件复用 Diff 标签；连续浏览文件使用预览标签。需要同时保留多个文件时，可通过编辑器将标签固定。

切换 CR 后，之前固定的 Diff 标签仍可查看，右侧编辑仍会修改真实工作区文件。要为当前 CR 添加代码选区评论，请从当前审阅树重新打开文件；旧 CR 的 Diff 不能用于给当前 CR 绑定评论。

勾选文件表示已审，勾选目录会处理目录下的变化文件。目录显示已审数量及“未审 / 部分已审 / 已审完”；未保存或读取失败的文件不会计为已审完。标题栏可展开或折叠全部目录，常规刷新保留手动展开状态。

已审判断比较左右两侧的内容、文件类型和执行权限，不使用 commit ID。因此内容未变时 stage 或 commit 不会清除标记；内容变了会显示“需复审”，恢复原内容后可重新匹配。右键“查看上次审阅后的变化”查看上次已审的工作区快照到当前工作区的差异。

未保存的编辑会显示“未保存”，不能标为已审或新增代码选区评论。保存后再检查最新 Diff；已有评论不会因此删除。

## 写评论与复核回复

点击文件可写文件评论；点击目录名称或右键“评论此目录”，可写针对目录及其子目录的整体意见。目录评论不绑定行号，也不计入已审文件数。

对代码选区评论时，先在完整 Diff 选中代码，再点击“评论所选内容”。评论保存片段与前后上下文，最多选择 200 行；行号仅作提示。片段唯一匹配时可跟随行数变化；代码改变或存在多个匹配时会提示确认，不按旧行号猜测位置。

编辑评论在原卡片中进行，使用“保存修改 / 取消编辑”，不会新增一条评论。“删除”把评论移入当前文件或目录的“已删除”恢复区，可撤销；它不影响文件的已审标记。解决评论和标记文件已审是两个独立操作。

“待处理评论”显示本轮所有未解决意见，支持直接编辑、解决、删除和打开位置。目录收起后仍汇总子树评论数；目录评论区可跳转到有评论的子目录与文件。即使文件不再有 Diff 或路径已被删除，原评论仍可查看；改名不会自动转移评论。

## 交给 Agent

点击“交给 Agent”将说明复制到剪贴板，再粘贴给能够访问该项目的 Agent。ReviewSlate 不调用模型、不发送消息，也不自动启动 Agent。只想自己处理时，可以直接在待处理评论概览中完成复核。

交接固定到 `.code-review/reviews/<CR ID>/PENDING.md`，切换 CR 不会使已复制的说明转向另一轮。顶层 `.code-review/PENDING.md` 只是当前 CR 的便捷副本，不适合当作长期交接地址。完整规则由项目内自动生成的 `.code-review/README.md` 提供。

交接说明与清单含绝对路径，清单还可能含原代码和上下文。远程路径属于远端文件系统，接收方需有相应访问能力；向外部模型或他人分享前，先检查这些内容。

待处理 Markdown 清单用于导航，长评论可能只显示摘要；Agent 处理前应按评论 ID 读取原评论与回执 JSON，以获得完整正文和选区上下文。

Agent 的处理顺序是：

1. 读取交接指定的 `REVIEW.json`，核对 CR、分支、固定基点和删除状态。记录已归档或删除、检出分支不符时停止，不自动切分支。
2. 按该轮清单中的稳定评论 ID 读取原评论，结合当前代码确认位置。目录评论的 `target` 为 `directory`；文件评论有 `anchor` 时包含代码选区。
3. 修改与验证后写入 `.code-review/replies/<评论 ID>.json`，先写临时文件，再重命名替换。保留原评论，不代替用户解决。
4. 用户刷新并检查回复，再标为已解决。匹配当前 `revision` 的回复显示“Agent 已回复，待复核”；修改评论正文或重新打开已解决评论会使旧回复失效。

回执结构如下；占位值必须替换为原评论中的实际值：

```json
{
  "version": 1,
  "commentId": "<原评论 id>",
  "commentRevision": "<原评论 revision>",
  "body": "说明修改、验证结果或无法处理的原因。",
  "updatedAt": "<ISO 8601 时间>"
}
```

## 管理多轮 CR

同一仓库中，每个“分支 × 固定基点”对应一条未归档 CR。每个分支记住最后使用的一轮；切回分支或重新打开项目后接续它。换基点会进入另一轮，进度、评论和草稿按 CR 隔离。

分支身份使用完整分支名，普通提交不会改变它；重命名分支视为新分支，旧记录仍在。游离 `HEAD` 按检出的提交区分。打开其他分支的记录只提示你先切分支，不执行 checkout。

“归档”保留进度、快照与评论，可从已归档分组恢复。归档当前 CR 后不会自动选中其他记录；再次选择相同基点会创建干净的新 CR。恢复旧 CR 前，若已有相同分支和基点的新记录，需先归档新记录。

“永久删除这条 CR…”会在确认后清理该轮保存的记录、快照、评论、回执和相应备份，不能恢复，也不修改代码或其他 CR。失败时显示“删除未完成 · 可重试”，可再次执行清理。删除范围与备份注意事项见[数据说明](data.md)。
