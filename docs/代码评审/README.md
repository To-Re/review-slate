## 本轮发现与复核

### DOC-01：永久删除失败的阶段不能合并（P2，已修正）

原[设计规范](../设计/README.md)及两份[用户文档](../用户文档/使用指南.md)把永久删除失败或中断统一描述为“删除未完成 · 可重试”。实际 [`ReviewState.purge()`](../../src/state.ts) 先归档并使交接失效，再保存 v4 删除标识；前一阶段失败时尚可恢复，标识持久化后的清理失败才禁止恢复。[`ReviewHistory`](../../src/history.ts) 也按 `purgePending` 区分“已归档”和“删除未完成”。原表述会使读者找错恢复入口或误判数据已不可恢复。

修订已分别写入设计规范第 145 行、使用指南第 93 行及[数据与故障处理](../用户文档/数据与故障处理.md)第 38 行，与[数据协议](../客户端/数据协议.md#归档评论删除与永久删除)的分阶段说明一致。审核者回读了三处最终正文并核对源码，复核通过。没有修改删除实现。

### DOC-02：退出不保证取消在途任务（P2，已修正）

原[客户端说明](../客户端/README.md)声称刷新不会脱离扩展生命周期继续运行。实际 `enqueue()` 只在动作开始前检查 `disposed`；`dispose()` 清理计时器、监听器与映射，不取消已开始的异步动作，动作结束后仍会调用 `render()`。若把原表述当作适配契约，会错误假定关闭时已无在途 I/O 或后续渲染。

客户端说明第 42 行现已限定为阻止尚未开始的任务，并明确在途动作没有取消或等待完成保证。审核者回读并复核通过。未来新宿主的取消和关闭等待仍需设计、实现与验证，不能把本次文案修正当作生命周期实现已完善。

另已复核客户端说明中的职责残留：本地接口、存储与宿主适配统一由客户端研发负责，不再要求与另设的“核心研发”方向协调。
