# 使用指南

本文帮助你用 ReviewSlate 完成一轮人工审阅，并在代码继续变化后接着审。适用于 1.0.1 VSIX；安装步骤及实机验证范围见[项目首页](../../README.md#安装)。本文由写作角色维护，最后核查于 2026-11-03；业务规则以[产品文档](../产品/README.md)为准。

Codex 候选版使用独立的工作区和数据目录，见 [Codex 使用指南](Codex使用指南.md)。下文的原生 Diff 编辑、编辑器菜单与 `.code-review/` 均指 VSIX。

## 先选好仓库和基点

打开至少有一个提交的 Git 项目，在活动栏进入 ReviewSlate。顶部“审阅设置”显示当前仓库与默认基点；多仓库工作区先确认选中了要审阅的仓库。每个仓库分别保存设置和审阅记录。

在“审阅记录”中点击“新建审阅…”或标题栏加号，选择本轮的对比起点。

| 选择方式 | 固定的基点 | 适合的任务 |
| --- | --- | --- |
| 选择本地或远端分支 | 该分支与当前 `HEAD` 的共同祖先 | 审阅当前分支从主分支分出后的变化 |
| 选择一个提交 | 该提交本身 | 从指定版本或某次提交开始审阅 |

选好后，基点固定为完整 SHA；后续主分支或 `HEAD` 移动不会改变它。“对比起点”显示来源、提交说明与短 SHA，可用旁边的复制按钮获取完整 SHA。扩展读取已有 Git 数据，不会自动 fetch；需要更新远端引用时，先自行完成更新。

提交选择框可以搜索最近 150 条提交，也可以直接粘贴任意本地提交的完整 SHA 或至少 7 位短 SHA，按回车验证，不受最近记录数量限制。找不到或有歧义时，修改原输入后重试；取消不会创建记录或改变当前 CR。

“默认基点”只影响以后选择基点时的优先项，不改变当前 CR。你可以把常用的本地分支、远端分支或固定提交设为默认值。

### 从 Git 图形中的提交开始

在提供相应扩展菜单的 Trae / Trae CN 中，可右键单个提交，选择“ReviewSlate：以此提交为基点新建审阅”。它使用该节点所属仓库和提交，对比当前检出分支的工作区，不会切换到被点击的提交。

普通发布扩展不能保证原版 VS Code 显示这项 Git 图形菜单；汇总节点和多选也不适用。菜单不可见时，复制提交 ID，通过命令面板执行“ReviewSlate：从提交 SHA 新建审阅…”，或使用“审阅记录”更多菜单里的同名操作。

## 看清这轮比较的内容

点击“变更文件”里的文件打开完整 Diff。左侧是固定基点，右侧是当前仓库**磁盘上已保存的工作区**。它包含相对基点的分支提交、暂存与未暂存改动合成后的最终内容，以及未被 Git 忽略的未跟踪文件。

暂存区没有独立的一侧。例如，你把一处修改暂存后，又在工作区把它改回基点内容，这处修改不会仅因仍在暂存区就显示出来。Git LFS、换行规范化等过滤器也可能使这里的结果与 Git 自身的 Diff 不同，原因见[比较与容量限制](数据与故障处理.md#比较与容量限制)。

普通 UTF-8 工作区文件可以在完整 Diff 的右侧直接编辑、保存。左侧基点、上次审阅后的增量视图、删除文件、符号链接、二进制以及纯类型或权限摘要只读。编辑器可能已经显示你尚未保存的输入，审阅状态仍按磁盘内容计算；出现“未保存”时，先保存，再检查最新 Diff。

同一 CR 的同一文件复用 Diff 标签，连续浏览默认使用预览标签。需要并排保留多个文件时，用编辑器的固定标签功能。切换 CR 后，旧的固定标签仍可查看；其中可编辑的右侧仍是真实工作区文件，保存会修改代码。为当前 CR 写代码选区评论时，应从当前审阅树重新打开文件。

## 记录已审进度，再看后续变化

勾选文件表示已经检查当前内容；勾选目录会处理目录下的变化文件。目录显示已审数量以及“未审 / 部分已审 / 已审完”，未保存或读取失败的文件不会计为已审完。“变更文件”标题栏提供刷新、展开和折叠全部目录操作，普通刷新会保留手动展开状态。

ReviewSlate 通过两侧内容、文件类型和执行权限识别已审状态。因此，只做 stage 或 commit、内容没有变化时，标记仍然有效；内容变化后显示“需复审”，恢复原内容后可重新匹配。

复审时，右键文件选择“查看上次审阅后的变化”，查看上次标记已审时的工作区快照与现在的差异。检查完后重新标记已审，后续增量就以这次内容为准。这份快照只帮助续审，不是完整的版本历史或仓库备份。

## 把评论写在合适的范围

| 意见针对什么 | 怎样写 |
| --- | --- |
| 整个文件 | 点击文件，在“审阅评论”中输入正文并保存 |
| 一段代码 | 在本工具的完整 Diff 中选中代码，点击“评论所选内容”，确认选区后写正文并保存 |
| 目录及其子目录 | 点击目录名称或右键“评论此目录”，写整体意见 |

代码选区最多 200 行。评论会保存所选片段与前后文，行号只作提示：内容仍能唯一匹配时可以跟随行数变化；代码改变或出现多处匹配时会提示确认，保留原片段供你判断。文件改名不会自动转移评论。工作区侧有未保存编辑时，先保存再选中代码添加评论；已有评论不会因此删除。

“编辑”在原评论卡片中修改正文，用“保存修改 / 取消编辑”结束操作。“删除”将单条评论移入该文件或目录的“已删除”恢复区，可以撤销。**解决、删除评论都不会替你标记文件已审；勾选已审也不会自动解决评论。**

点击“待处理评论”，集中检查本轮所有未解决意见，可直接编辑、解决、删除或打开位置。目录收起时仍汇总子树评论数；目录评论区也可跳转到有评论的子目录与文件。文件不再有 Diff 或路径已删除时，原评论仍可查看。

自己处理意见时，修改并保存代码，复审变化，再把确认完成的评论标为已解决。需要继续处理的已解决评论可以重新打开。

## 可选：交给 Agent 处理

![从固定基点、记录意见到 Agent 处理与人工复核的可选协作流程](../../media/review-flow.png)

上图是选择 Agent 协作时的流程示意，不是界面截图。ReviewSlate 负责整理本地资料和展示回复；你决定交给谁，并对结果做最后复核。

1. 本轮有未解决评论时，点击“交给 Agent”，将交接说明复制到剪贴板。
2. 检查说明中的仓库、CR 与资料范围，再粘贴给能够访问该项目的 Agent。远程工作区中的路径属于远端，接收方需要相应访问能力。
3. Agent 按生成的 `.code-review/README.md` 读取该轮状态、待处理清单和完整评论，在你的授权范围内修改与验证，并写入对应回执。
4. 回到 ReviewSlate 刷新。匹配当前评论版本的回执显示“Agent 已回复，待复核”；检查代码、回复和实际验证结果，复审受影响的文件，再决定是否解决评论。

按钮只复制文字，不会启动 Agent、发送消息或调用模型。交接说明与清单包含绝对路径，选区评论还可能包含原代码和上下文；粘贴到外部服务前先检查这些内容。插件不联网，并不代表你自行选择的 Agent 不会联网。

交接绑定 `.code-review/reviews/<CR ID>/PENDING.md`，切换 CR 不会让已复制的地址指向另一轮。顶层 `.code-review/PENDING.md` 会随当前 CR 改变，仅作为便捷副本。清单中的长内容可能被摘要化，Agent 需要按评论 ID 读取原 JSON，不能只靠摘要修改代码。

Agent 应核对本轮 CR、分支、基点和当前评论版本；分支不符或记录已归档、删除时停止处理，不自行切分支。回执单独保存，不改写原评论，也不代替你点击“已解决”。评论正文修改或已解决评论重新打开后，旧回执不再表示当前意见已处理。同一条评论应交给一个写入者，避免并行回复互相覆盖。需要开发集成时，读取[数据协议](../客户端/数据协议.md)，字段与安全检查不在本指南重复维护。

## 接着审，或结束一轮

每个仓库按“分支 × 固定基点”保留未归档 CR。再次选择已有组合时，会打开原记录并保留进度与评论；换基点会进入另一轮。每个分支记住最后使用的 CR，切回分支或重新打开项目后可接续已保存的数据。当前版本尚未完成“关闭重开后恢复文件选择、目录展开和 Diff 定位”的整体验收，不应把进度保存理解为所有导航位置都能恢复。

普通提交不会改变分支身份。重命名分支会被视为新分支，旧记录仍在；游离 `HEAD` 按检出的提交区分。打开其他分支的记录时，先在编辑器或 Git 中自行切换分支，再返回 ReviewSlate。

结束前，检查本轮变化文件是否已审，是否还有未保存、读取失败或需复审的文件，再核对待处理评论。归档操作本身不证明这些检查已经完成。

| 操作 | 保存的数据与后续行为 |
| --- | --- |
| 归档 | 保留进度、快照和评论，可从“已归档”分组恢复；归档当前 CR 后不会自动选中其他记录 |
| 归档后新建同一组合 | 创建干净的新 CR；若要恢复旧 CR，需先归档相同分支与基点的新记录 |
| 永久删除这条 CR | 确认后清理该轮记录、快照、评论、回执及对应备份，扩展内不可恢复；不修改代码或其他 CR |

永久删除在早期失败时，记录可能仍位于“已归档”，尚可恢复；删除标识保存后的清理失败才显示“删除未完成 · 可重试”，此时只能继续清理。按实际分组和错误提示处理，具体阶段见[数据、隐私与故障处理](数据与故障处理.md)。
