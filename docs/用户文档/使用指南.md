# 使用指南

维护责任：写作；状态：现行；最后核查：2026-11-03。本文适用于正式版 1.0.2 VSIX；安装、升级和实机验证范围见[项目首页](../../README.md#安装)，版本变化见 [CHANGELOG](../../CHANGELOG.md)。业务规则以[产品文档](../产品/业务规则.md)为准。

一轮审阅称为 CR。先选仓库和固定基点，再逐个查看变化、记录已审内容与意见。代码继续变化后，回到这轮 CR 复审；是否使用 Agent 由你决定。

## 1. 选择仓库和固定基点

打开至少有一个提交的 Git 项目，从活动栏进入 ReviewSlate。在顶部“审阅设置”确认仓库；多仓库工作区可点击仓库项切换，每个仓库分别保存默认基点和 CR。从项目子目录打开时，审阅范围仍是 Git 仓库根目录。

在“审阅记录”点击“新建审阅…”或标题栏加号，选择本轮起点：

| 选择方式 | 固定的基点 | 适合的任务 |
| --- | --- | --- |
| 本地或远端分支 | 该分支与当前 `HEAD` 的共同祖先 | 审阅当前分支从主分支分出后的变化 |
| 一个提交 | 该提交本身 | 从指定版本或某次提交开始审阅 |

选好后，“对比起点”显示来源、提交说明和短 SHA，旁边的复制按钮可取得完整 SHA。后续分支或 `HEAD` 移动不会改变这个基点。扩展只读取已有 Git 数据；若需要更新远端引用，请先自行 fetch。

提交选择框可以搜索最近 150 条记录，也可以直接粘贴任意本地提交的完整 SHA 或至少 7 位短 SHA。输入的提交不受列表范围限制；找不到或有歧义时可以修改原输入重试，取消不会改变当前 CR。“默认基点”只影响以后选择时的优先项，不改变现有 CR。

同一仓库、分支和固定基点已有未归档 CR 时，会接续原记录，保留进度与评论；选择不同组合会进入另一轮。

### 从提交 SHA 或 Git 图形进入

命令面板中的“ReviewSlate：从提交 SHA 新建审阅…”可直接接受提交 ID；“审阅记录”的更多菜单也有同名操作。

在提供相应菜单的 Trae / Trae CN 中，还可右键 Git 图形里的单个提交，选择“ReviewSlate：以此提交为基点新建审阅”。它使用该节点所属仓库和提交，对比当前检出分支的工作区，不会切换到被点击的提交。汇总节点和多选不适用；原版 VS Code 不保证显示这项菜单，缺少时使用 SHA 入口。

## 2. 打开 Diff，确认正在比较的内容

点击“变更文件”中的文件，打开完整 Diff。左侧是固定基点，右侧是**磁盘上已保存的工作区**。它展示相对基点的最终内容，包括分支提交、暂存与未暂存改动，以及未被 Git 忽略的未跟踪文件。

暂存区没有独立的一侧。例如，一处修改已经暂存，随后又在工作区改回基点内容，这处修改不会仅因暂存区仍有差异而出现。Git LFS、换行规范化等过滤器也可能使结果与 Git 自身的 Diff 不同，见[比较与容量限制](数据与故障处理.md#比较与容量限制)。

普通 UTF-8 工作区文件可以在完整 Diff 右侧编辑、保存。左侧基点、上次已审后的增量视图、删除文件、符号链接、二进制与类型或权限摘要只读。编辑器可能显示尚未保存的输入，审阅状态仍按磁盘计算；看到“未保存”时，先保存，再检查最新内容。

同一 CR 的同一文件复用 Diff 标签，连续浏览默认使用预览标签；要并排保留多个文件，可使用编辑器的固定标签功能。切换 CR 后旧标签可能仍在，其中可编辑的右侧仍指向真实工作区文件，保存会修改代码。要为当前 CR 写代码选区评论，请从当前审阅树重新打开文件。

## 3. 记录已审内容和意见

检查完文件后，勾选它以记录当前内容。勾选目录会批量处理其下的变化文件；目录显示已审数量和“未审 / 部分已审 / 已审完”。未保存或读取失败的文件不能计为已审完。“变更文件”标题栏可以刷新、展开或折叠全部目录，普通刷新保留手动展开状态。

评论按意见范围选择入口：

| 意见范围 | 操作 |
| --- | --- |
| 整个文件 | 点击文件，在“审阅评论”输入正文并保存 |
| 一段代码 | 在本工具的完整 Diff 中选中代码，执行“评论所选内容”，确认范围后保存 |
| 目录及其子目录 | 点击目录名称或右键“评论此目录”，输入整体意见并保存 |

代码选区为 1 至 200 行。工作区侧存在未保存编辑时，先保存再选区。评论保留原片段和上下文：内容仍能唯一匹配时可跟随行号变化，内容改变或位置不确定时会提示人工确认；文件改名不会自动转移评论。

在原卡片中点击“编辑”，用“保存修改 / 取消编辑”结束编辑。删除单条评论后，可在该文件或目录的“已删除”区撤销。文件不再有 Diff 或路径已删除时，原评论仍可查看。

**已审进度与评论状态分别维护。** 勾选文件不自动解决评论，解决或删除评论也不自动把文件标为已审。目录收起后仍汇总子树评论数量；点击“待处理评论”可集中编辑、解决、删除未解决意见，或打开对应位置。

## 4. 代码变化后继续复审

ReviewSlate 按两侧内容、文件类型和执行权限识别已审状态。内容没变时，stage 或 commit 不会清空标记；内容变化后显示“需复审”，恢复到已审内容时可重新匹配。

复审时，右键文件选择“查看上次审阅后的变化”，比较上次标记已审时的工作区快照与现在的内容。检查后重新标记已审，后续增量就以这次内容为准。快照用于接续审阅，不能代替完整仓库备份。

自己处理评论时，先修改并保存代码，复审变化，再把确认完成的意见标为已解决。需要继续处理的已解决评论可以重新打开。新建、读取、保存或刷新出现错误时，先处理原因，不把空列表当成“全部审完”；排查入口见[数据与故障处理](数据与故障处理.md#遇到问题时)。

## 可选：把待处理意见交给 Agent

![固定基点、记录意见、交给 Agent、修改与回复、人工复核](../../media/review-flow.png)

图中是选择 Agent 协作时的流程示意，不是界面截图。ReviewSlate 整理本地资料并展示回执，最后由你复核。

1. 本轮有未解决评论时，点击“交给 Agent”，复制交接说明。
2. 检查说明中的仓库、CR 和资料范围，再粘贴给能访问该项目的 Agent。Remote SSH 中的路径属于远端，接收方需要相应访问能力。
3. Agent 按生成的 `.code-review/README.md` 核对本轮状态，读取完整意见，在你的授权范围内修改、验证，并写入对应回执。
4. 回到 ReviewSlate 刷新。匹配当前意见的回执显示“Agent 已回复，待复核”；检查修改、回复和实际验证，复审受影响文件后，再决定是否解决评论。

“交给 Agent”只复制文字，不启动 Agent、不发送消息、不调用模型。说明和清单含绝对路径，选区意见还可能含代码；交给外部服务前先检查资料和接收方。扩展不联网，并不约束你另行选择的 Agent。

交接固定到 `.code-review/reviews/<CR ID>/PENDING.md`，切换 CR 不会改变已复制的目标。顶层 `.code-review/PENDING.md` 随当前 CR 改变，只是便捷副本。清单可能缩短长内容，Agent 必须读取完整评论，不能只依据摘要修改代码。

Agent 应核对 CR、分支、基点和评论版本；分支不符、记录归档或已删除时停止，不自行切分支或改处理另一轮。回执单独保存，不改原评论，也不替你解决意见。修改正文或重新打开评论后，旧回执不再代表当前版本已处理；同一条评论应交给一个写入者。集成细节见[数据协议](../客户端/数据协议.md)。

## 5. 离开、接续或结束一轮

每个分支记住最后使用的 CR。切回分支或重新打开项目后，可接续已保存的进度和评论；这不等于所有文件选择、展开状态和 Diff 光标位置都能恢复，完整导航恢复尚未验收。离开前先保存要保留的评论，草稿与已保存评论不同。

打开其他分支的记录前，应自行切到对应分支。普通提交不会改变分支身份；重命名分支会被视为新分支，旧记录仍保留；游离 `HEAD` 按检出的提交区分。移动仓库目录或换编辑器不自动迁移审阅资料。

结束前，核对变化文件的已审状态，处理未保存、读取失败和需复审项，再检查待处理意见。归档操作本身不证明这些工作已经完成。

| 操作 | 结果 |
| --- | --- |
| 归档 | 保留进度、快照和评论，可从“已归档”分组恢复；归档当前 CR 后不会自动选中另一条 |
| 归档后新建同一组合 | 创建干净的新 CR；恢复旧 CR 前，需先归档同分支同基点的新记录 |
| 永久删除这条 CR | 确认后清理本轮记录、快照、评论、回执和对应备份；扩展内不可撤销，不修改代码或其他 CR |

永久删除失败时，以实际分组为准：“已归档”中的记录可能仍可恢复；“删除未完成 · 可重试”只能继续清理。不要手改删除标识恢复旧资料，阶段与恢复边界见[数据与故障处理](数据与故障处理.md#归档删除与恢复的区别)。
