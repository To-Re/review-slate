# 数据与故障处理

维护责任：写作；状态：现行；最后核查：2026-11-03。适用范围：正式版 1.0.2 VSIX。本版性能修复不改变数据格式和存储位置；日常操作见[使用指南](使用指南.md)，字段、归属和恢复规则以[客户端数据协议](../客户端/数据协议.md)为准。

## 完整审阅数据分布在两处

| 位置 | 保存的内容 | 备份时需要注意 |
| --- | --- | --- |
| 当前宿主分配的 ReviewSlate 扩展存储 | 默认基点、CR 目录、已审记录、内容快照 | 按仓库实际根路径区分；扩展安装目录不是数据目录 |
| 仓库根 `.code-review/` | 评论、Agent 回执、已删除评论恢复区、交接清单、永久删除标识 | 不包含完整 CR 和已审进度，不能单独恢复一轮审阅 |

仓库选择、评论草稿等界面状态由编辑器另外保存。草稿不等于已保存评论，也不保证包含在上面两处备份中；需要保留的正文应先保存为评论。

不同编辑器、本地与远端扩展宿主各自保存数据，没有自动同步、导入或迁移工具。移动仓库目录、换机器或打开另一个 worktree，会改变存储对应关系。即使复制了 `.code-review/`，新位置也不保证能把评论接到原 CR。

## 备份与恢复

当前没有一键导出，也没有扩展内的数据目录定位入口。备份前需确认**当前扩展宿主实际提供的数据目录**：它由宿主按扩展 ID `to-re.code-review` 分配，对应开发接口 `globalStorageUri`。不同编辑器、配置和远程环境的位置可能不同，不能用安装 VSIX 的扩展目录代替；Remote SSH 的数据在远端。

确认位置时，对照[数据协议中的目录说明](../客户端/数据协议.md#数据真源与存储位置)：已建立 CR 的扩展数据目录会按仓库路径哈希分区，保存 CR 目录和该轮状态。不要仅凭发现同名目录就覆盖或迁移。不能确认实际位置时，先保留现状并向宿主维护者核实；只备份 `.code-review/` 仍是不完整备份。

### 留下一份完整备份

1. 保存代码和需要保留的评论，记下当前仓库路径、分支、CR 和完整基点 SHA，便于恢复后核对。若要保留未保存草稿，先另存正文。
2. 停止所有访问这两处数据的扩展宿主与 Agent 写入任务，避免复制过程中数据继续变化。
3. 完整复制对应扩展的数据目录，以及仓库根 `.code-review/`。两处应来自同一停写时点；保留 `.bak`、删除标识和其他辅助文件，不只挑选评论 JSON。
4. 若要恢复当时的代码，另外备份 Git 对象和未提交文件。已审快照只保存审阅所需内容，不能替代代码备份。

备份可能包含代码、评论和路径，应按原项目资料的权限保管。保存两处文件不等于已经验证能够恢复，重要资料应在受控副本中核对完整性。

### 恢复后确认归属

恢复前先保留当前两处数据的副本，并停止相关写入者。恢复同一时点的扩展存储与 `.code-review/`，在相同宿主、相同仓库路径下重开，核对分支、完整基点 SHA、CR、已审数量与评论是否属于原来的一轮。

当前没有跨机器、跨编辑器或移动仓库路径的自动恢复能力。不要只把一份旧评论或旧 CR 目录拷回去：它可能与另一处的新状态或永久删除标识冲突。损坏文件、关联快照和历史格式的处理见[数据协议](../客户端/数据协议.md#失败处理与恢复)。

## 归档、删除与恢复的区别

| 操作 | 是否可恢复 | 数据影响 |
| --- | --- | --- |
| 归档 CR | 可从已归档分组恢复；同分支同基点已有活动记录时需先处理冲突 | 保留进度、快照和评论，不释放评论容量 |
| 删除单条评论 | 可从对应对象的已删除区撤销 | 保留恢复资料，不等于彻底清除本轮数据 |
| 永久删除 CR | 进入删除标识阶段后，扩展内不可撤销 | 清理本轮可识别的记录、快照、评论、回执和备份，不修改工作区代码及其他 CR |

永久删除可能分阶段失败。在保存删除标识之前失败时，记录可能仍在“已归档”，尚可恢复或再次删除；保存标识之后清理失败时，会进入“删除未完成 · 可重试”，只能继续清理。按实际分组和错误提示操作，不手动移除标识复活旧记录。

永久删除不会清除你另存的备份、全部编辑器缓存或无法识别的旧草稿，也不是磁盘安全擦除。详细清理顺序与兼容边界见[数据协议](../客户端/数据协议.md#归档评论删除与永久删除)。

## 本地保存与分享范围

扩展运行时不联网、不上传代码、无遥测，没有 HTTP 监听服务。Git 操作只读，不执行 fetch、checkout、提交、索引写入或仓库过滤器。你在完整 Diff 右侧编辑并保存时，仍会实际修改工作区文件。

首次保存评论会创建 `.code-review/`；首次保存或接续已有评论时，会按需向根 `.gitignore` 追加有效的 `/.code-review/`，保留原内容。已被 Git 跟踪的资料不会因此取消跟踪，提交前应自行核对。已有非空目录缺少有效工具标识时，扩展会报错而不会覆盖。

两处审阅数据均未加密。快照保存代码，评论可能保存选区和上下文，Agent 交接说明与清单还包含仓库和文件的绝对路径。“交给 Agent”只复制文字，由你决定接收方；把文字粘贴到外部服务后，资料如何处理取决于接收方。

公开 Issue、日志或截图前，应去掉真实代码、内部信息和个人路径；不要直接上传整个 `.code-review/` 或扩展存储。

## 比较与容量限制

| 情况 | 当前处理方式 |
| --- | --- |
| 较大的变化文件 | 单侧上限 5 MiB；一次扫描中变化文件两侧内容累计上限 80 MiB。未变化的大文件可经校验跳过 |
| 二进制或非 UTF-8 文件 | 显示摘要，不提供普通文本编辑和选区评论体验 |
| 符号链接 | 读取链接文本，不跟随目标文件；存储路径中的符号链接会被拒绝 |
| 子模块 | 需单独打开为仓库审阅 |
| Git LFS、换行规范化或其他过滤器 | 按磁盘原始字节比较，不执行 clean、textconv、external diff 或换行转换，可能与 Git 自身展示不同 |
| 评论容量 | 普通评论区和已删除恢复区分别最多 2,000 条，跨 CR 计数；已解决评论也计入，归档不释放容量 |
| 代码选区 | 1 至 200 行，通过片段和上下文定位，不做 AST 跟踪或自动改名迁移 |

读取失败、合并冲突、损坏快照或超限不会被视为“没有变化”，也不能产生已审成功结果。先处理提示中的原因，再刷新核对。完整容量与校验规则见[数据协议](../客户端/数据协议.md#完整备份与容量)。

## 遇到问题时

| 看到的情况 | 可以先做什么 |
| --- | --- |
| 没有 ReviewSlate，或找不到仓库 | 确认扩展已启用、内核兼容，工作区受信任且为文件系统目录，仓库至少有一个提交，当前宿主能运行 Git。Remote SSH 还要确认远端安装 |
| Git 图形没有新建审阅菜单 | 复制提交 SHA，在命令面板执行“ReviewSlate：从提交 SHA 新建审阅…” |
| 升级后仍出现旧版行为 | 保存代码与评论，重载所有正在使用 ReviewSlate 的编辑器窗口；Remote SSH 还需确认远端安装并重载对应窗口，避免旧扩展宿主继续运行 |
| 新建后树展示慢，或打开 Diff 慢 | 确认已安装 1.0.2 并重载窗口；记录宿主版本、文件数、变更规模、是否正刷新及可重复操作。性能测量范围见[验证记录](../测试/验证记录.md)，不要清空进度尝试提速 |
| 文件显示“未保存”，不能勾选或给工作区侧代码添加选区评论 | 保存后从当前 CR 打开文件，确认最新 Diff 再操作 |
| 提示 CR、分支或内容已变化 | 刷新并核对当前仓库、分支和 CR，再重新打开目标；不要借旧 CR 标签为当前 CR 写选区评论 |
| 评论保存报错，但似乎已经出现 | 保留草稿，先刷新核对。评论可能已保存，只是交接清单生成失败；不要立即另建相同评论 |
| 评论无法定位或文件已改名 | 查看原片段与上下文，人工确认位置；扩展不会按旧行号猜测或自动迁移评论 |
| 数据文件损坏或主文件缺失 | 保留主文件、`.bak` 和现状副本。扩展不会自动采用备份或空进度；核对归属、格式与快照完整后再人工恢复 |
| 提示另一写入者或残留锁 | 停止相关写入者；只有确认没有进程仍在写入，才按数据协议处理残留 `write.lock` |
| 永久删除未完成 | 从对应记录再次执行永久删除；不要清除删除标识后继续使用旧资料 |

仍无法解决时，在 [Issue](https://github.com/To-Re/review-slate/issues) 提供版本、环境、复现步骤、预期和实际结果。优先使用合成仓库，附脱敏后的错误文本；安全问题按 [SECURITY.md](../../SECURITY.md) 报告。
